## 1. TL;DR

The raw `Surfs` section is **21.2 %** positional-byte match (native 8961 B, editor 8930 B). ✅
The mismatched bytes are **two object-table-INDEX fields plus a small pBase tail**:

| surf field | kind | nat B | ed B | positional match | identical / 485 |
|---|---|--:|--:|--:|--:|
| `iActor` | **export** index (owning brush) | 844 | 813 | **0.0 %** | 0 |
| `texture_ref` | **import** index | 485 | 485 | **0.0 %** | 0 |
| `pBase` | index (Points pool) | 905 | 905 | **87.4 %** | 373 |
| poly_flags | value | 1940 | 1940 | 100 % | 485 |
| vNormal | index (Vectors) | 485 | 485 | 100 % | 485 |
| vTextureU | index (Vectors) | 485 | 485 | 100 % | 485 |
| vTextureV | index (Vectors) | 485 | 485 | 100 % | 485 |
| iLightMap | index (LightMap) | 905 | 905 | 100 % | 485 |
| iBrushPoly | value | 485 | 485 | 100 % | 485 |
| iZone | value pair | 1940 | 1940 | 100 % | 485 |

Field-wise (alignment-independent) that is: `iActor` + `texture_ref` fully diverge (0/485 each), and
`pBase` has a **genuine ~114-byte residual** (112 of 485 surfs differ, NOT a cascade artifact — it is
measured field-aligned). `pBase` indexes the Points pool, whose own byte-parity is a **separate,
still-open** port (§82b §3.B #4, board point-pool item); it is not an object-table-ref problem and is
tracked there, not here. The seven remaining fields are byte-exact. ✅

## 2. Why the section collapses to 21 % (the cascade)

`iActor` is the last field of each surf and its **width matches only 274/485** (native `{1B:126,
2B:359}` vs editor `{1B:157, 2B:328}`): a differing width shifts the *next* surf's start, and that
shift cascades through all the byte-exact middle fields — dragging a field-wise ~84 % down to the
interleaved 21 %. ✅ The width boundary is export index 63 (ref = idx+1 = 64 → 2-byte compact index);
native and editor put **different** brushes below/above 63.

`texture_ref` is 1 byte on **every** surf both sides (width 485/485) — so it never shifts anything; it
is a flat 485 B of in-place value loss. Consequently **fixing texture values alone is worthless**
(21.2 % → 21.3 %, harness row `Tx`): the `iActor` cascade swamps it. Texture only pays off once
`iActor` alignment is fixed (row `B+` below). ✅

## 3. The divergence is an object-table-INDEX ORDER difference — the names ARE in the trunk ✅🔬

Both fields resolve to the **correct referent**: per-surf `iActor` name 485/485 and `texture_ref`
name 485/485 match. Only the compressed-int *index* differs. And the trunk **carries the names**:
95 of 96 brush names are byte-identical between NativeCastle and Test_Castle (only the builder brush
differs, `Brush0` vs `Brush1`), and the texture names all match. So this is **purely an ordering
problem** — what differs is the editor's *assignment of table indices*, i.e. the order objects land
in the export/import tables. It is NOT that the trunk lacks the identities. ✅

Against the golden `Test_Castle.dx`, that ordering is **not** any obvious deterministic function of
the trunk (🔬, all measured on the one golden — see the oracle caveat in §5):
1. **Export order ≠ Actors[] order.** Export #0 is a `Light` (`Moon_c6irpg`); `LevelInfo0`, which is
   `Actors[0]`, is export **#8**. The brush block is non-contiguous (exports 39, 41, 42, 43, 44, gap
   45, 46 …). ✅
2. **Export order ≠ trunk order.** The editor's brush-actor export order matches trunk order only for
   the first two brushes then diverges (editor #3 = `RoofNW`, trunk #3 = `WallLeft`). The import table
   is likewise interleaved (`Engine` package at import index 3, textures between classes). ✅
3. **Not FName-hash and not lexicographic.** Same-prefix, random-suffix names **cluster** in the
   export table (`Moon_*` at #0–#5, `MoonFill_*` near #9–#14), and the order is not alphabetical
   either — so both a name-hash (which keys on the random suffix and would scatter them) and a plain
   name sort are excluded. 🔬 **Caveat:** clustering also fits a deterministic *name-grouped* or
   paste-duplication rule, so it rules OUT hash/lexicographic but does not by itself *prove* a
   session artifact — the dispositive test is §5's oracle question.

## 4. Reachability ceilings (`surf_ref_order_analysis.py`, full offset sweep) ✅

| candidate | Surfs raw % | note |
|---|--:|---|
| A  baseline native | **21.2 %** | current |
| C1 brush block in **trunk (file) order** | **39.9 %** | deterministic (best @offset 43) |
| C2 brush block in **first-reference order** | 39.9 % | deterministic (best @offset 43) |
| C3 brush block **name-sorted** | 25.3 % | deterministic (best @offset 33) |
| D  editor brush **ORDER**, compacted | 92.1 % | order is session; isolates ORDER vs offset |
| B  each brush its **editor-EXACT** index | 93.3 % | session order |
| B+ editor-EXACT `iActor` **and** `texture_ref` | 98.7 % | remainder ≈ pBase ~114 B |

Reading this: the dominant lever is the brush **ORDER**, not the block offset — candidate D (the
editor's own brush order, merely compacted to small indices) already reaches **92.1 %**, essentially
the full B ceiling, while trunk order at the *same* region tops out at **39.9 %**. So a
deterministic, trunk-only reorder is worth **~+19 pts** (21→40), NOT the ~+3 an earlier
scan-truncated sweep suggested; but climbing from ~40 % to ~92 % requires the editor's *brush
ordering itself*, which — against this golden — diverges from every trunk-derivable order tested
(§3). `texture_ref` adds the last ~5 pts only after `iActor` is aligned (B→B+); the final ~1.3 %
is the pBase tail (§1), owned by the point-pool port.

## 5. THE decisive question — which oracle? (follow-up spike) 🔬

Everything in §3–§4 is measured against the **hand-authored** `Test_Castle.dx`, whose object-table
order is *that map's authoring-session history* (many CSG rebuilds, moves, paste-duplications). But
`direction/materialize.md`'s fidelity bar is **"byte-identity with UnrealEd's build of the same trunk"** — what
UnrealEd emits when it **imports our T3D trunk fresh**. A clean `MAP IMPORT` might create actors (and
number exports) in **T3D/trunk order**, which is deterministic and which native could then match — in
which case candidate C1's 39.9 % is the wrong number and true reachable parity could be far higher
(if the editor re-import also lands brushes near offset ~43, approaching D's 92 %).

**This is untested** — no editor-materialized-from-trunk castle exists on disk. It is THE thing that
decides whether per-surf `iActor`/`texture_ref` byte-parity is reachable or a dead end, and it is a
prerequisite for spending any effort on an assembly-side export reorder. Concretely: `level
materialize` (editor path) the castle trunk, then run `surf_ref_order_analysis.py` against *that*
output and read whether its brush/texture export order is trunk-order (deterministic → pursue a
reorder) or scrambled like Test_Castle (session → exclude, as §82b §3.A). Flagged on the board
(`inbox`). Until that runs, the honest bounded statement is:

> **Against the available (hand-authored) golden, the Surfs residual is an object-table-index ORDER
> difference with a ~40 % deterministic-from-trunk ceiling; reaching ~92 % needs the editor's own
> brush ordering, which this golden does not expose as trunk-derivable. Whether a clean editor
> re-import IS trunk-derivable is unmeasured and is the gating follow-up.**

No assembly reorder was landed: it is premature until §5 is settled, and even the best deterministic
option changes bytes in the ref-bearing sections (Surfs/Zones/Lights/`MyLevel.Actors`) whose editor
values are themselves session-ordered — a guarded change to make only if the oracle spike says trunk
order matters.

## 6. What is NOT the problem (ruled out this session) ✅

- Not a wrong texture: per-surf texture **name** resolves 485/485; only the import *index* differs.
- Not a wrong owning brush: per-surf `iActor` **name** resolves 485/485; only the export *index* differs.
- Not the field order: `iLightMap`/`iActor` on-disk order is already correct (§20 §14 fix holds).
- Not (mostly) geometry: the only non-ref residual is `pBase` (87 %, ~114 B), owned by the still-open
  Points-pool port (§82b §3.B #4), not by this export/assembly layer.
